I. Adding the meta-mender-rockchip-optee layer to your build
=================================================

Before the first build/run, generate OP-TEE TA signing keys:

```
cd kas/demos/meta-mender-rockchip-optee/recipes-security/optee/files/keys
./generate_keys.sh
```

This creates `ta_sign_key.pem` and `ta_public_key.pem`, which are required by
the OP-TEE recipes during parsing/build.

Build with kas using the demo configuration:

Run 'kas build kas/demos/rock-4c-plus-enc.yml'

II. Purpose
===========

The layer contains an example setup for a Yocto build which enables
OP-TEE on Rockchip-based boards.

The example demonstrates secure-world bring-up and OP-TEE integration in the
boot chain, with userspace access through the Linux TEE subsystem.

III. Included functionality
===========================

The OP-TEE setup includes:
- Trusted Firmware-A (BL31) and OP-TEE (BL32) integration in the boot flow
- OP-TEE device tree integration (`linaro,optee-tz` / `method = smc`)
- Linux TEE subsystem support (`/dev/tee0`, `/dev/teepriv0`)
- `tee-supplicant` userspace support for normal-world/secure-world RPC

For a detailed step-by-step boot and runtime sequence, see:
- `OPTEE_BOOTFLOW.md`

That document describes the full chain from BootROM and SPL through TF-A,
OP-TEE, U-Boot, Linux TEE probe, and userspace TA interaction.

IV. Key generation note
======================

This demo uses two different key flows:

1) TA signing keys (build-time)
- Trusted Applications are signed using an RSA key pair generated by:
    `recipes-security/optee/files/keys/generate_keys.sh`
- The script creates:
    - `ta_sign_key.pem` (private signing key)
    - `ta_public_key.pem` (public key)
- Generate these before the first `kas build ...` to avoid missing
    `ta_sign_key.pem` parse/checksum errors.

2) Runtime encryption keys (first boot)
- For the encrypted-image flow (`core-image-enc`), key material is generated in
    secure world on first boot and persisted in OP-TEE secure storage (RPMB).

In short:
- First boot: key is generated and used to initialize/open the encrypted volume.
- Later boots: the stored key is unsealed and reused to open the volume.

For the detailed runtime sequence, see:
- `OPTEE_BOOTFLOW.md`
